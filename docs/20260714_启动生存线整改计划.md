# 启动生存线整改计划

## 背景

启动链路的底线不是“能写日志”或“进程还活着”，而是必须至少走到：

- 主窗口或快速设置窗口可见；
- 后端就绪信号已发出；
- 自动更新检查 worker 已注册；
- 前端能够继续加载会话并打开对话窗口，或明确进入可操作的恢复界面。

凡是达不到这条生存线的失败，都可能让用户安装到一个无法自我更新、无法进入应用的版本。

## 目标

把启动前的非必要历史兼容和数据修复动作从“硬阻塞”改成“可降级”。真正仍允许阻断启动的，只保留运行环境级失败，例如无法创建当前数据目录、Tauri 运行时无法启动、应用窗口系统无法运行。

## 整改项

### 1. 旧配置目录迁移失败时直接跳过旧目录，读取新目录

现状：

启动时如果发现旧配置目录存在、新配置目录不存在，会尝试把旧目录整体改名到新目录。一旦改名失败，应用状态初始化失败，程序在窗口和自动更新启动前退出。

问题：

旧目录迁移只是历史兼容，不是当前版本启动的必要条件。迁移失败可能来自旧目录被占用、杀毒软件拦截、目标路径异常、跨卷或文件系统限制等。这些不应该让新版本完全打不开。

目标行为：

- 优先使用新配置目录。
- 如果新配置目录不存在而旧配置目录存在，可以尝试迁移。
- 如果迁移成功，继续使用新目录。
- 如果迁移失败，记录 warn/error，创建并使用新的空配置目录继续启动。
- 不因为旧目录迁移失败阻断窗口显示和自动更新 worker 注册。
- 后续可以在界面中提示“旧数据自动迁移失败”，并给出手动导入/诊断入口。

验收标准：

- 模拟旧目录存在但不可重命名时，应用仍能打开窗口。
- 自动更新 worker 仍会注册。
- 新配置目录会被创建并用于本次启动。
- 日志里能看到旧目录迁移失败原因。

### 2. 配置文件损坏时备份并生成默认配置

现状：

配置解析失败会向上返回错误，可能中断前端启动快照读取或配置加载。

目标行为：

- `app_config.toml` 读取成功但解析失败时，不直接阻断启动。
- 将损坏文件备份为带时间戳的 `.bak` 文件。
- 写入一份默认可启动配置。
- 启动后提示用户配置已重置，并保留原文件位置。

验收标准：

- TOML 损坏时应用仍能进入窗口。
- 默认配置可被加载。
- 原损坏配置被备份。
- 用户能看到明确提示，而不是停在加载中。

### 3. 会话 V1 到 V2 迁移只执行一次，坏 V1 直接放弃

现状：

会话 V1 到 V2 的版本迁移仍残留 `blocked`、前端确认抛弃、单会话错误向外返回失败等语义。它看起来像一个长期恢复门闩，而不是一次性版本升级。

问题：

V1 到 V2 的正确模型是一次性迁移：

- 是否需要执行只看记录的会话迁移版本，不以“磁盘上是否还有旧文件”为触发条件；
- 能读、能转换的 V1 会话写入 V2；
- V1 会话坏了、读不了、ID 不合法、结构不合法时，直接放弃该 V1 会话；
- 迁移命令完成后推进到 V2 版本；
- 后续启动只读 V2，不再扫描 V1；
- 不存在“隔离坏 V1 并在每次启动继续处理”的长期状态。

因此，单个 V1 会话坏掉不是迁移失败，而是本轮迁移的丢弃项。只有当前数据目录不可写、磁盘不可用、基础 SQLite/文件系统不可用这类系统级问题，才允许阻断。

目标行为：

- 移除 V1 到 V2 启动门闩里的 `blocked` 语义。
- 移除“用户确认后抛弃异常会话”的启动交互。
- `run_message_store_migration` 不因为单个 V1 会话损坏返回失败。
- 迁移过程中重新读取 V1 会话失败、会话 ID 不合法、V1 manifest 不可用时，计入 discarded/failed 统计并继续。
- 迁移完成后推进 `message_store_migration_version`，后续只看 V2。
- 旧文件扫描只允许作为本次版本迁移内部的输入枚举；版本已到位时绝不再因为旧文件存在而触发迁移。
- 日志记录被放弃的 V1 会话 ID 与原因，便于排查，但不阻断启动。

验收标准：

- 存在损坏 V1 会话时，迁移命令仍返回成功报告。
- 可转换 V1 会话正常进入 V2。
- 损坏 V1 会话不会阻断版本推进。
- 迁移完成后再次启动不再检查 V1。
- 前端不再出现 V1 迁移 blocked 确认界面。

### 4. V3 元数据迁移保持单会话跳过模型，清理残留不阻断版本推进

现状：

V3 聊天元数据迁移已经基本采用单会话导入失败就跳过的模型，但全局尾部仍有一些清理动作可能返回失败，例如删除已迁移的 V2 metadata 文件。

问题：

V3 迁移的版本推进也不应被非必要清理动作阻断。已成功导入 V3 的会话应以 V3 为准；旧 V2 metadata 清理失败只代表残留文件没有删掉，不应该让启动或版本迁移失败。

目标行为：

- 单个 V2 会话导入 V3 失败时继续跳过并记录日志。
- 已完成导入的会话标记迁移完成。
- 全局 V3 版本可以在可处理项完成后推进。
- 删除旧 V2 metadata 文件失败时只记录 warn，不回滚、不阻断版本推进。
- 未完成 storage operation 的恢复若遇到业务数据异常，优先按 operation 维度放弃或清理；只有 SQLite/文件系统基础能力不可用时才返回失败。

验收标准：

- 存在损坏 V2 会话时，V3 迁移仍能完成全局版本推进。
- 已成功导入 V3 的会话可正常显示。
- 旧 V2 metadata 删除失败不会让迁移命令失败。
- 再次启动以 V3 状态为准，不重新依赖已放弃的 V2 会话。

### 5. 明确仍允许致命退出的边界

以下失败仍可视为致命：

- 无法解析或创建当前版本的数据目录；
- 当前数据目录没有基本读写权限；
- Tokio/Tauri 运行时无法初始化；
- Tauri app run 失败；
- 平台窗口系统无法创建任何窗口。

这些情况应用层很难继续运行，但需要尽可能提供清楚的系统级错误提示或日志。

## 实施顺序

1. 先改旧配置目录迁移失败的降级逻辑。
2. 再改配置损坏备份与默认配置恢复。
3. 调整会话 V1 到 V2 迁移：移除 blocked/确认抛弃模型，坏 V1 直接计数放弃并推进 V2。
4. 调整 V3 迁移尾部清理与未完成 operation 恢复，避免非系统级问题阻断版本推进。
5. 增加启动生存线验证用例和手工检查清单。

## 验证清单

- 旧配置目录存在且重命名失败，应用仍打开。
- `app_config.toml` 损坏，应用仍打开并生成默认配置。
- 单个 V1 会话损坏，V1 到 V2 迁移仍完成并推进版本。
- 单个 V2 会话损坏，V3 迁移仍完成并推进版本。
- Windows 安装版启动后自动更新 worker 仍会注册。
