# 20260628 会话级快速请求记录统一化重构计划

## 一、背景

当前项目里已经存在多类“快速请求”：

- 远程联系人秘书判断
- 远程联系人忙碌中的主动引导判断
- 会话标题生成
- 任务草稿优化
- 工具审查相关的快速模型判断

这些请求都具有相似特征：

- 不是正式聊天消息
- 不调用工具
- 只产生一段请求文本与一段回复文本
- 更适合作为会话运行过程中的辅助记录，而不是混入正式消息流

目前这些能力分散在不同入口中，记录方式不统一，有的只写日志，有的只保留解析结果，有的没有稳定的会话内可见记录。后续如果要做排障、回放、审查展示、标题链路解释与工具审查追踪，就会持续碰到“每个场景各记各的”的问题。

因此，本轮重构目标是建立一套统一的“会话级快速请求记录”机制，让所有快速请求都按时间顺序挂在所属会话下追加写入，并在归档时整体清空。

## 二、目标

本轮最终目标如下：

1. 每个会话都具备自己的快速请求记录表。
2. 快速请求记录按时间顺序追加写入，只增不删，不做中途编辑。
3. 快速请求记录不混入正式聊天消息，也不伪装成 assistant / user message。
4. 远程联系人、会话标题生成、任务草稿优化、工具审查这几类快速请求统一落入这张会话级记录表。
5. 会话归档时清空该会话的快速请求记录。
6. 前后端读取语义统一为“按会话读取”，不引入全局快速请求池。

## 三、范围

本轮范围明确包含以下三类来源：

### 1. 远程联系人

- 秘书判断
- 忙碌中的主动引导判断
- 后续同类轻量裁决入口

### 2. 会话标题生成与任务轻量生成

- 会话自动标题生成请求
- 后续若存在标题回退 / 重生成，也应视为同类快速请求
- 任务草稿优化这类“快速生成结构化结果”的轻量请求也纳入同一体系

### 3. 工具审查

- 工具安全审查
- 工具审查中的快速模型判断
- 后续同属“快速请求而非正式委托 / 正式聊天”的审查型入口

本轮不包含：

- 正式聊天消息持久化重构
- 委托会话记录重构
- 模型底层 provider 日志系统重构
- usage 统计口径改造

## 四、核心设计

### 1. 数据归属

快速请求记录直接归属到 `Conversation`。

不建立全局表，不建立跨会话索引，不引入独立的快速请求会话类型。

原因如下：

- 快速请求本质上是会话运行过程中的辅助痕迹
- 用户后续查看时，天然也是从“当前会话发生过什么快速判断”出发
- 标题生成、工具审查、远程联系人判断都可以稳定映射到某个会话

### 2. 数据结构原则

数据结构保持极简，只表达“这次快速请求说了什么、回了什么、结果如何、发生在何时”。

本轮不要求在记录层表达复杂业务语义：

- 不区分人格身份
- 不记录工具调用
- 不把快速请求包装成消息角色
- 不在记录层做额外逻辑拆分

建议字段方向：

- `id`
- `request_text`
- `response_text`
- `success`
- `error`
- `model_name`
- `duration_ms`
- `created_at`

如需最小来源标识，可保留一个轻量 `kind` 字段，仅用于区分：

- `remote_im`
- `title_generation`
- `task_optimization`
- `tool_review`

但这只是展示与筛选辅助，不承载复杂业务判断。

### 3. 生命周期

快速请求记录的生命周期严格跟随会话：

- 会话运行中可持续追加
- 切前后台不清空
- 普通切换会话不清空
- 会话归档时整体清空

本轮不支持：

- 删除单条记录
- 编辑单条记录
- 跨会话迁移记录

### 4. 与正式消息的边界

快速请求记录不是聊天消息，因此必须保持边界清晰：

- 不进入 `Conversation.messages`
- 不参与上下文窗口计算
- 不参与压缩摘要
- 不进入正式导出消息流
- 不影响 unread / last assistant / last user 等消息语义字段

### 5. 与底层模型调用日志的边界

快速请求记录与底层 provider 调用日志并存，但职责不同：

- 底层调用日志关注 provider 请求过程
- 快速请求记录关注会话视角下的业务痕迹

本轮不以“替代现有调用日志”为目标，而是补上一层稳定的会话级业务记录。

## 五、链路要求

### 1. 写入要求

所有快速请求入口都必须统一走会话级追加写入。

要求如下：

1. 在请求发起前或请求完成后，能够拿到所属 `conversation_id`
2. 成功时写入请求文本、回复文本、成功标记、模型信息、耗时
3. 失败时写入请求文本、错误信息、失败标记、模型信息、耗时
4. 解析 JSON 成功与否不应影响原始回复文本记录

### 2. 读取要求

读取语义统一为“按会话读取快速请求记录”。

本轮不要求一开始就做复杂分页，但必须保证后续能平滑扩展：

- 当前会话读取
- 轻量快照附带最近若干条
- 详情面板按会话读取完整记录

### 3. 归档要求

会话归档时，快速请求记录必须一并清空。

这里的“清空”是产品语义要求，不保留到归档历史中。

因此本轮必须明确：

- 归档操作如何触发清空
- 归档恢复 / 取消归档是否不回填旧记录
- 相关测试 fixture 与默认值如何同步

## 六、分阶段实施

### 阶段一：建立会话级数据模型

目标：

- 给 `Conversation` 增加快速请求记录字段
- 补齐默认值、序列化、fixture、读写链路
- 保证旧数据兼容

完成标准：

- 老会话数据可无损读取
- 新字段缺失时自动回退为空列表
- 正常保存 / 读取 / 切会话不出错

### 阶段二：建立统一写入入口

目标：

- 抽出统一的快速请求写入 helper
- 收口“成功写入”和“失败写入”的公共动作
- 避免每个业务入口手写一套 append 逻辑

完成标准：

- 远程联系人、标题生成、任务草稿优化、工具审查都能复用同一写入入口
- 原始请求文本与原始回复文本都能稳定落盘

### 阶段三：接入远程联系人

目标：

- 秘书判断记录写入会话
- 主动引导判断记录写入会话

完成标准：

- 每次远程联系人快速判断后，都能在所属会话看到顺序追加的记录
- 成功与失败都能留下痕迹

### 阶段四：接入会话标题生成与任务轻量生成

目标：

- 标题生成不再只留下结果标题
- 而是把标题生成快速请求本身也写入会话记录
- 任务草稿优化这类轻量结构化生成请求也写入所属会话记录

完成标准：

- 触发标题生成后，可追溯当时发送给快速模型的文本与返回内容
- 任务草稿优化后，也能在所属会话追溯请求与返回内容

### 阶段五：接入工具审查

目标：

- 工具审查中的快速模型判断统一接入会话级记录
- 与现有工具审查结果、批次、报告保持边界分离

完成标准：

- 工具审查相关快速请求可从所属会话追溯
- 不破坏现有工具审查列表、详情、报告结构

### 阶段六：读取与展示收口

目标：

- 为前端提供稳定的按会话读取接口
- 明确哪些快照接口需要带最近记录，哪些详情接口读全量

完成标准：

- 当前会话能稳定读取快速请求记录
- 不把工具审查、标题生成、任务轻量生成、远程联系人各自做成多套独立读取协议

### 阶段七：归档清空接入

目标：

- 归档时清空快速请求记录
- 明确与归档、恢复、删除等生命周期动作的关系

完成标准：

- 归档后该会话快速请求记录为空
- 相关回归测试补齐

## 七、风险与注意事项

### 1. 不要把快速请求继续伪装进正式消息系统

如果把快速请求再塞进消息流，会重新引入上下文污染、导出污染、摘要污染与消息读取热路径负担。

### 2. 不要让不同业务入口各自维护独立结构

如果远程联系人、标题生成、工具审查各自挂不同存储，最终还是会回到“到处都是半套记录”的局面，失去这次重构意义。

### 3. 归档清空必须是明确产品语义

一旦定义为“归档即清空”，后续实现就不能再偷偷把这类记录带进归档恢复、消息导出或历史审计里。

### 4. 读取链路要避免把整会话重读问题重新带回来

快速请求记录挂在会话上之后，前台快照、工具审查、会话列表等高频入口不能顺手变成“每次整读完整记录”。必须按使用场景定义轻量读取与详情读取边界。

### 5. 标题生成、任务轻量生成与工具审查都不是远程联系人特例

这次重构不是“给远程联系人顺手加记录”，而是建立统一基础设施。标题生成、任务轻量生成与工具审查必须从一开始就在计划里作为一等场景考虑。

## 八、验收口径

本轮完成后，需满足以下验收口径：

1. 每个会话都能独立持有自己的快速请求记录。
2. 远程联系人、标题生成、任务草稿优化、工具审查这几类快速请求都能写入同一套记录结构。
3. 记录只增不删，按时间顺序追加。
4. 快速请求记录不混入正式消息，不参与消息上下文与导出。
5. 会话归档后，快速请求记录被清空。
6. 读取接口按会话统一，不再为各类快速请求场景各做一套孤立协议。

## 九、本轮不展开的内容

以下内容不在本计划本轮交付范围内：

- 快速请求独立线程 / 独立 runtime 设计
- 快速请求专用 UI 形态最终定稿
- 快速请求全局检索
- 快速请求跨会话统计
- 快速请求 usage / provider 原始日志统一改造

以上能力如果后续需要，应建立在本次“会话级统一记录”基础之上继续扩展。
