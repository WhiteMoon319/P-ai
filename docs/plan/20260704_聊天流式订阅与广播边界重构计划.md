# 聊天流式订阅与广播边界重构计划

## 背景

当前聊天流式链路同时存在三类通道：

- `send_chat_message` 调用携带的一次性 `onDelta` channel。
- `bind_active_chat_view_stream` 建立的当前会话流式 channel。
- `easy-call:*` / `chat.*` 这类全局事件广播。

这几类通道在代码里职责边界已经漂移：有些高频流式事件会走到全局事件路径，有些低频关键节点又依赖流式 channel 承载，前端也需要在多处兜底、缓存、重绑。结果是协议不够清楚，切会话、多端打开、后台会话同时运行时都容易出现性能压力和时序歧义。

这次按严格重构处理，先收口协议边界，再迁移实现。

## 目标约束

1. 没有任何前端打开或订阅的会话，不推送高频流式内容。
2. 前端切换会话后，旧会话对该前端的高频推送资格必须立即失效。
3. 高频流式推送必须由前端主动申请，后端不能因为会话在运行就默认向所有端推 token。
4. 保持多端同时推送：同一个会话可被多个窗口、Web 侧边栏、VS Code 侧边栏同时订阅并接收流式。
5. 关键节点走全局低频广播，包括工具执行节点、工具完成、上下文整理节点、消息完成、轮次完成等。前端收到广播后，如果发现广播属于当前打开会话，则走“切到本会话/恢复本会话”路径，由该路径主动建立或刷新流式 channel。

## 协议分层

### 高频流式事件

只能通过会话订阅 channel 发送：

- assistant token delta
- reasoning delta
- 流式活动投影
- 大体积或逐步变化的 `streamCache`
- 工具流式投影块

这些事件默认不走全局广播。它们可以不强制每条携带完整 `conversationId`，因为 channel 的订阅关系已经表达归属；但订阅建立、终态、错误、调试日志必须带 `conversationId` / `requestId` / `activationId`。

### 低频关键广播

可以走全局广播，但 payload 必须小而稳定：

- `history_flushed`
- `round_started`
- `round_completed`
- `round_failed`
- `stream_rebind_required`
- `tool_started`
- `tool_completed`
- `tool_failed`
- `context_compaction_started`
- `context_compaction_completed`
- `assistant_message_committed`
- `conversation.runtimeStateUpdated`

广播必须带 `conversationId`，可以带 `requestId` / `activationId` / `phaseId` / `toolCallId` / `toolName` / `status` / 简短摘要。广播禁止携带 token 增量、大段 assistant 正文、大型工具结果、完整 stream cache。

### 后端缓存

后台运行但无订阅者的会话仍继续更新后端运行缓存与持久化：

- stream cache 作为切回会话后的恢复真源。
- 关键节点照常广播，用于列表状态、通知、侧边栏摘要和前端自愈。
- 没有订阅者时不发送高频流式事件。

## 后端方案

### 1. 建立统一订阅模型

把“当前活动聊天流绑定”收口成明确的订阅表：

- key：`conversation_id`
- value：多个订阅者
- 订阅者字段：`subscriber_id`、`window_label` 或端类型、`conversation_id`、`channel`、`subscription_id`、`created_at`、`last_seen_at`

桌面聊天窗口仍保持单窗口单会话语义：同一 `window_label` 新订阅一个会话时，旧订阅立即失效。Web / VS Code 侧边栏可以作为独立订阅者存在，同一会话可有多个订阅者。

### 2. 明确订阅命令语义

现有 `bind_active_chat_view_stream` 语义调整为“订阅当前会话高频流式”：

- 输入必须包含明确 `conversationId`。
- 空 `conversationId` 表示取消当前窗口订阅。
- 不再使用 `*` 通配绑定接收后台会话 token。
- 返回 `subscriptionId`，用于日志、调试、后续可选的过期事件丢弃。

新增或补齐 `unbind_active_chat_view_stream`：

- 前端切到空会话、窗口关闭、组件卸载时调用。
- 后端发送失败时仍保留现有 prune 机制，清理失效订阅。

### 3. 拆分派发函数

把当前混合职责拆开：

- `dispatch_stream_delta_to_subscribers(...)`：只查订阅表并向订阅者发送高频流式。
- `emit_chat_checkpoint_broadcast(...)`：只发送低频关键节点广播。
- `update_conversation_stream_runtime_cache(...)`：继续只维护后端缓存，不负责决定前端推送范围。

派发入口必须先分类事件：

- 高频事件：更新后端缓存，然后只发订阅 channel。
- 低频事件：更新必要状态，然后发全局广播。
- 同时具备两类语义的节点拆成两个事件：一个小广播，一个可选的订阅流式投影。

### 4. 收口 `send_chat_message` 直连 channel

`send_chat_message` 传入的 `onDelta` 不能继续作为绕过订阅表的高频旁路。

推荐迁移方式：

1. 前端发送前先确保当前会话已订阅。
2. `send_chat_message` 的 `onDelta` 只保留 accepted / history / terminal 等低频回执，或直接复用订阅表中的 channel。
3. 如果第一步改动过大，可过渡为：登记 `onDelta` 时同时记录 `window_label + conversation_id + subscription_id`，每次发送前确认该窗口仍订阅该会话，否则丢弃高频 delta。

最终目标是：所有高频流式只经过统一订阅表。

### 5. 保留多端能力

现有 VS Code / Web 侧边栏如果需要实时 token，应接入同一套订阅语义，而不是依赖 `chat.assistantDelta` 全局通知。

如果某端只需要列表状态和消息完成提醒，只消费低频广播即可。

## 前端方案

### 1. 会话切换即订阅切换

当前打开会话变化时：

- 新会话存在：调用 `bindActiveConversationStream(conversationId, true)`。
- 新会话为空：调用 unbind。
- 切换成功后，本窗口旧会话订阅失效。

这条链路应集中在现有会话切换 / 恢复 orchestrator 中，不在消息渲染组件里散落调用。

### 2. 广播只做唤醒，不承载流式

前端监听关键广播后：

- 若 `payload.conversationId !== 当前打开会话`，只更新列表状态、缓存摘要或忽略。
- 若属于当前打开会话，调用现有“切到本会话 / 恢复本会话”入口，让该入口主动拉 snapshot 并建立流式订阅。
- 不在广播 handler 中直接拼 token、直接追加 assistant 文本、直接应用大型 stream cache。

### 3. 降级 `handleExternalAssistantDelta`

现有 `handleExternalAssistantDelta` 只能保留为兼容低频或过渡逻辑：

- 不再处理普通 token delta。
- 不再作为后台会话 stream cache 的主要来源。
- 如果收到旧协议高频事件，调试模式下记录告警，正常模式下丢弃或只触发当前会话恢复。

### 4. 当前会话恢复路径保持权威

用户切回一个正在后台运行的会话时：

1. 前端拉当前会话轻量快照 / runtime snapshot。
2. 用后端 stream cache 恢复当前可见投影。
3. 主动订阅该会话后续高频流式。

不新增直接整读完整消息集的恢复路径。

## 实施阶段

### 阶段一：事件分类与观测

- 梳理所有 `AssistantDeltaEvent.kind` 和 `easy-call:*` / `chat.*` 事件用途。
- 新增后端分类 helper：高频流式、低频广播、内部事件。
- 加调试日志计数：高频事件发送目标数、无订阅者跳过数、全局广播事件类型。
- 不改变业务行为，只为后续重构提供可验证口径。

### 阶段二：后端订阅表收口

- 改造 `active_chat_view_bindings` 为多订阅者模型或在现有结构外新增统一订阅管理层。
- 移除 `*` 通配高频接收语义。
- `bind_active_chat_view_stream` 返回订阅信息。
- 增加 unbind 命令与失效订阅清理。

### 阶段三：高频派发只走订阅

- 拆分 `dispatch_assistant_delta_to_active_view`。
- 高频事件只发订阅者 channel，不再调用全局 assistant delta 广播。
- 无订阅者时只更新后端 stream cache 并记录 debug 计数。
- 保证同一会话多订阅者同时收到流式。

### 阶段四：低频广播协议化

- 明确关键节点广播 payload。
- 将工具开始 / 完成、上下文整理、消息提交等节点从流式 channel 依赖中剥离。
- 前端广播 handler 只负责判断当前会话并触发恢复 / 订阅，不直接拼流式内容。

### 阶段五：`send_chat_message` 旁路收口

- 发送前确保当前会话订阅存在。
- 将 `send_chat_message` 的直连高频 channel 迁移到订阅表，或加订阅有效性校验作为过渡。
- 删除或降级不受订阅约束的高频发送路径。

### 阶段六：清理兼容逻辑

- 删除旧的全局高频 `assistantDelta` 处理分支。
- 删除前端依赖广播拼 stream cache 的兜底逻辑。
- 收敛 debug 面板中的订阅计数、pending channel 计数和 active binding 计数命名。

## 验收标准

1. 50 个后台会话同时流式时，当前窗口只收到当前订阅会话的高频 delta。
2. 当前窗口切换到会话 B 后，会话 A 的后续 token 不再发送到该窗口。
3. 无任何订阅者的会话运行时，后端只更新 stream cache，不发送高频 channel 事件。
4. 同一会话被两个端同时打开时，两个端都能收到该会话后续流式。
5. 工具开始、工具完成、上下文整理、消息完成等关键节点仍能全局广播。
6. 当前打开会话收到关键广播后，能通过恢复路径主动建立或刷新流式 channel。
7. 全局广播 payload 不包含 token 增量、大段正文、大型工具结果或完整 stream cache。
8. 切回后台流式会话时，可以从后端 stream cache 恢复当前显示并继续接收后续流式。

## 验证计划

- Rust：新增订阅表与事件分类的定向单测。
- Rust：覆盖“无订阅者不发送高频”“同会话多订阅者都发送”“切换订阅后旧订阅不发送”。
- 前端：为会话切换订阅、广播唤醒当前会话、旧高频广播丢弃增加最小相关测试。
- 类型检查：涉及前端事件类型变化时运行 `pnpm typecheck`。
- 后端检查：涉及 Rust 类型 / 命令签名变化时运行 `cd src-tauri && cargo check`，如默认 target 被占用则使用约定的 `CARGO_TARGET_DIR=target-tests`。

## 非目标

- 不重写模型供应商流式解析。
- 不改变会话调度并发策略。
- 不把每个 token 强制改成携带完整 `conversationId`。
- 不引入“前端先接收所有 token 再过滤”的方案。
- 不新增完整读取 `Conversation.messages` 的恢复路径。
- 不把低频广播升级成大 payload 同步通道。

## 风险与回滚

- 风险：某些端之前依赖全局 `chat.assistantDelta` 接收 token，迁移后会失去实时流式。
  - 缓解：先盘点桌面、Web 侧边栏、VS Code 侧边栏消费者，再逐一接入订阅。
- 风险：切会话时 unbind / bind 时序导致短暂漏 token。
  - 缓解：切入会话先拉 stream cache，再订阅后续；高频流不保证 replay，恢复以后端缓存为准。
- 风险：工具节点既有流式投影和关键广播混杂，拆分后 UI 状态丢失。
  - 缓解：工具节点第一版只广播小状态，详细投影仍通过订阅 channel 给当前会话。
- 回滚：保留旧事件名一小段兼容期，但在分类层禁止高频事件进入全局广播；若端能力未迁移完成，可临时只对该端启用显式订阅。

## 待确认问题

1. 是否保留 `easy-call:assistant-delta` / `chat.assistantDelta` 事件名作为低频兼容事件，还是新增更准确的 `chat.streamCheckpoint` / `chat.nodeUpdated`。
2. `send_chat_message` 的 `onDelta` 是直接降级为低频回执，还是第一阶段先记录订阅身份做过渡校验。
3. Web / VS Code 侧边栏是否需要完整 token 流式；如果需要，应定义它们的订阅生命周期。
