# 20260627_远程IM秘书接力与在场门卫机制计划

## 一、目标

本次计划用于重新定义远程 IM 场景里秘书与助理的接力关系，重点修正“秘书何时参与、何时退出、何时重新进入”的机制边界。

这次只冻结需求，不写实现方案，不讨论线程、调度器、状态存储、接口字段和提示词拼装细节。

本次只解决三个核心问题：

1. 助理正在处理一波消息时，积压消息应如何续跑
2. 助理完成当前一波处理后，秘书是否应重新参与下一波入口判断
3. 秘书如何以委托形式出现，同时保持只判断、不执行

## 二、前提共识

本计划基于以下前提：

1. 远程 IM 消息无论命中什么机制，都会先进入会话历史
2. 秘书参与与否，只影响“是否交给助理回复”，不影响消息持久化
3. 秘书本质上是判断者，不是执行者
4. 助理本质上是执行者，不是每条消息入口都必须重新授权的对象

因此，这套机制要区分两种完全不同的场景：

1. 当前这一波消息还没处理完
2. 当前这一波已经处理完，下一波消息刚刚到来

## 三、角色边界

### 3.1 秘书

秘书只负责一件事：

- 判断新到的一波消息，是否值得让助理正式接手回复

秘书不负责：

- 直接回复远程联系人
- 调用工具
- 处理中途插入接管已开始的助理轮次
- 对同一波积压消息反复做多次入口审核

### 3.2 助理

助理负责：

- 正式作答
- 消化当前轮次里的积压消息
- 在已接手的一波处理中持续续跑直到收尾

也就是说：

秘书决定“要不要开工”，助理负责“开工后把这一波做完”。

## 四、核心机制

## 4.1 离场时的新消息入口

当助理处于离场状态时，收到新消息后：

1. 消息先正常入历史
2. 由秘书做一次“是否需要回”的判断
3. 这次判断必须以委托形式存在

若秘书判定“不需要回”：

- 本轮结束
- 助理保持离场

若秘书判定“需要回”：

- 助理接手本轮回复
- 助理进入在场状态

## 4.2 助理处理中的积压续跑

这是本次最关键的边界。

当助理已经开始处理某一波消息，只要当前轮次结束时仍然存在积压消息，就应立刻继续由助理自己处理。

这里的要求是：

1. 不重新经过秘书
2. 不重新做入口判断
3. 不把同一波连续消息拆成“助理回一句，再秘书审一次”
4. 助理应连续消化，直到当前积压被清空

这部分语义要钉死：

积压续跑属于“同一波任务的延续”，不是“新一波消息的重新立项”。

## 4.3 助理收尾后的空闲门卫

当助理完成当前一轮回复后，需要立刻区分两种情况：

### 1. 仍有积压

若还有积压：

- 助理立刻继续处理
- 秘书不参与

### 2. 没有积压

若没有积压：

- 说明这一波处理已经正式收尾
- 从这一刻开始，后续新到的消息虽然仍发生在“在场期间”，但入口应重新交给秘书

这就是本次新机制的核心：

助理在场，不等于后续所有新消息都直接归助理。

只有“同一波尚未处理完的积压”才直接归助理；当前一波收尾后，下一波新消息应重新先过秘书。

## 4.4 在场期间的新一波消息

当助理仍保持在场，但上一波已经处理完、当前没有积压时：

1. 后续新消息正常入历史
2. 不论是否点名、不论内容强弱，先无条件激活秘书
3. 由秘书判断这条或这一批新消息是否需要助理再次接手

若秘书判定“需要回”：

- 助理再次接棒处理

若秘书判定“不需要回”：

- 助理保持在场待命
- 但本条消息不直接触发助理作答

这里的“无条件激活秘书”指的是：

只要进入的是“在场但空闲后的下一波消息”入口，就先让秘书参与判断，而不是让助理直接开答。

## 五、点名与关键字的语义

本轮机制下，点名、关键字、显式喊助理名字，仍属于消息特征的一部分。

但在“在场且空闲后的下一波消息”这个入口上：

1. 不再把“是否点名”作为秘书是否参与的前置开关
2. 而是统一先让秘书参与
3. 由秘书在判断时综合消息内容、点名情况和联系人规则决定是否需要助理接手

也就是说：

点名可以影响秘书结论，但不再决定秘书要不要出场。

## 六、委托可见性要求

秘书必须走委托机制，原因是要让本地用户能观察到秘书做过判断。

本次可见性要求如下：

1. 本地用户能看到秘书参与了一次判断
2. 本地用户能看到秘书的结论
3. 这份记录属于委托记录，不是工具记录
4. 远程联系人侧不应看到秘书内部过程

秘书虽然走委托，但它的委托是“判断型委托”，不是“执行型委托”。

## 七、秘书能力限制

秘书的能力边界需要固定为：

1. 不允许调用工具
2. 不允许直接发消息给远程联系人
3. 不允许替代助理完成正式回复
4. 不允许插入到助理正在续跑的积压处理中

秘书只负责在入口处做门卫判断。

## 八、状态语义

本次机制至少应满足以下状态语义：

1. 助理可以处于离场
2. 离场时，新消息先过秘书
3. 秘书放行后，助理接手并进入在场
4. 助理处理中的积压由助理自己连续消化
5. 助理处理完且无积压后，下一波新消息重新先过秘书
6. 在场不代表永久直通助理，只代表助理当前处于待命可接棒状态

这轮最需要避免的错误语义有两种：

1. 助理还没处理完当前积压，秘书就重新插进来
2. 助理明明已经收尾，后续所有新消息却永久绕开秘书

## 九、用户可感知体验

从用户视角，这套机制应表现为：

1. 助理不在场时，秘书先判断要不要让助理出来
2. 助理一旦出来，会把当前这一波连续消息尽量处理完
3. 助理忙完后，如果后面又来了新消息，还是先让秘书看一眼
4. 本地可以看到秘书什么时候做了判断
5. 对端只看到最终是否回复，看不到秘书内部流程

## 十、非目标

本计划暂时不覆盖以下内容：

1. 秘书提示词具体怎么写
2. 秘书委托用哪个部门、哪个人格
3. 委托会话怎么持久化展示
4. 在场多久自动离场
5. 多联系人并行时如何调度
6. 运行时字段、日志字段、埋点和界面样式

这些属于后续实现设计，不在本次需求冻结范围内。

## 十一、验收口径

只有同时满足以下条件，才算本次机制成立：

1. 离场时，新消息先由秘书以委托形式判断是否需要助理接手
2. 秘书不具备工具能力和直接回复能力
3. 助理接手后，当前积压消息由助理连续处理，不重新经过秘书
4. 助理完成本轮且仍有积压时，立即继续由助理续跑
5. 助理完成本轮且没有积压时，后续新到的一波消息重新先过秘书
6. 本地用户能够观察到秘书的判断记录
