# 20260627_调度中主动引导机制计划

## 一、目标

本次计划用于为“助理正在忙碌中又收到新消息”的场景补一层由秘书承担的主动引导判断机制。

目标不是直接新增一种强制打断，而是让秘书在助理忙碌期间，针对新到消息做一次快速判断：

- 这条新消息是否值得优先插队
- 是否应该打断当前助理的既有工作流
- 是否应该把这条消息提升为引导消息，交给现有引导续调度链路接管

本次只冻结需求，不写实现方案，不讨论模型调用代码、状态字段、日志细节和具体接口。

## 二、问题背景

当前机制里，助理一旦进入忙碌状态，新到消息通常只能排队等待。

这有一个明显缺口：

有些新消息虽然来得更晚，但优先级可能明显高于当前正在处理的激活消息。如果继续机械排队，会让助理错过更应该先看的内容。

但反过来，如果每来一条新消息都直接打断当前工作，也会让调度变得抖动、碎片化，甚至永远做不完当前任务。

因此，需要秘书补一层轻量判断：

不是“新消息一来就打断”，而是“先问一次，现在值不值得打断”。

## 三、核心机制概述

当 LLM 正在忙碌中，且会话在处理某条激活消息时，如果又来了新消息，则应触发一次秘书快速请求。

这次秘书快速请求的任务只有一件事：

- 结合当前正在处理的激活消息，以及刚到的新消息，判断是否应该让助理先看看这条新消息

若判断结果为“应该”：

- 将这条新消息升级为引导消息

若判断结果为“不应该”：

- 这条消息保持普通排队

这里的“打断”不是立即粗暴终止当前工具，而是借助现有 guided / 引导消息机制，让当前轮在合适检查点自然闭合，再由引导消息重开调度。

## 四、触发条件

只有同时满足以下条件时，才进入本次主动引导判断：

1. 当前会话存在正在运行中的助理调度
2. 当前助理处于忙碌状态
3. 有一条新的入站消息到达同一会话
4. 这条新消息当前还没有被升级为 guided

也就是说：

本机制只服务于“忙碌中又来新消息”的场景，不覆盖空闲会话，也不覆盖已经是 guided 的消息。

## 五、快速判断的输入

这次秘书快速请求必须至少拿到两类信息：

### 1. 当前激活消息

也就是：

- 当前助理之所以被激活、并仍在为之工作的那条消息或那一批核心消息

### 2. 刚到的新消息

也就是：

- 当前正在排队、但尚未接管助理注意力的这条新消息

本次判断的核心提问应当围绕下面这个语义：

助理正在为激活消息工作中，现在来了一条新消息，请判断是否应该打断当前工作，让助理先看看这条新消息。

这里的判断重点不是生成回复，而是判断优先级切换是否合理。

## 六、快速判断的输出语义

这次秘书快速请求的结论只需要表达一件事：

1. 应该优先看新消息
2. 不应该优先看新消息

若结论为“应该优先看新消息”：

- 这条消息应升级为引导消息

若结论为“不应该优先看新消息”：

- 这条消息继续保留普通排队状态

这个结果本质上决定的是：

- 是否让新消息获得一次引导插队资格

而不是：

- 是否立刻生成对新消息的正式回复

## 七、与现有引导机制的关系

本机制不是另起一套“打断协议”，而是秘书在忙碌期替 guided 做的一道前置门卫。

关系应明确为：

1. 秘书的主动引导判断只负责决定“要不要升级为 guided”
2. 一旦升级为 guided，后续仍走现有引导闭合与续调度语义
3. 不允许绕开既有 guided 收口路径，直接把新消息硬插进当前 provider 请求

换句话说：

本计划新增的是“guided 的升级门槛”，不是“guided 的执行机制”。

## 八、打断语义边界

这里的“打断”必须严格限定语义，避免误解成硬中断。

本次计划里的打断是指：

1. 当前调度在合适检查点闭合
2. 已完成的工作按既有规则落盘
3. 新消息作为 guided 被正式插入历史
4. 助理基于新引导消息重开下一轮调度

因此，本次不要求：

1. 立即中止正在执行的工具
2. 强行丢弃当前已完成的上下文与工具结果
3. 把新消息直接拼进当前尚未闭合的模型请求里

## 九、适用范围与非适用范围

本机制适用的，是“新消息可能比当前激活消息更值得先看”的场景。

本机制不应退化为：

1. 每来一条新消息都必跑一次快速模型
2. 每次快速模型判定都倾向于 guided
3. 只要 guided 就视为高优先级人工抢占

因此，本轮要钉死一个业务边界：

主动引导不是默认行为，而是秘书在忙碌场景下的一次优先级再评估。

## 十、用户可感知体验

从用户视角，这套机制应当表现为：

1. 助理正在处理一件事时，新消息不会一律死等
2. 秘书会先快速判断“这条新消息要不要先看”
3. 值得先看的消息，会自然触发一次引导式接管
4. 不值得先看的消息，继续排队，不打断当前工作

这样既避免迟钝，也避免过度抖动。

## 十一、非目标

本计划暂时不覆盖以下内容：

1. 秘书快速判断具体使用哪个模型
2. 秘书快速判断提示词具体怎么写
3. 如何抽取“当前激活消息”的最终数据结构
4. guided 升级命令的实现位置
5. 日志、埋点、调试面板展示
6. 是否对不同消息来源设置不同优先级策略

这些都属于后续实现设计，不在本次需求冻结范围内。

## 十二、验收口径

只有同时满足以下条件，才算本次机制成立：

1. 助理忙碌期间到来的新消息，能够触发一次由秘书承担的独立快速优先级判断
2. 这次秘书判断同时参考当前激活消息和刚到的新消息
3. 结论为“应该优先看”时，新消息会被升级为 guided
4. 结论为“不应该优先看”时，新消息继续普通排队
5. guided 接管仍沿用现有引导闭合与续调度语义，而不是另起一套硬打断机制
