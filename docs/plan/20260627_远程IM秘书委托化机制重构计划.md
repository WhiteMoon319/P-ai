# 20260627_远程IM秘书委托化机制重构计划

## 一、目标

本次改动用于重定义远程 IM 场景下“秘书”和“助理”的参与边界，解决当前秘书参与时机、可见性和在场切换语义不稳定的问题。

这次先钉死需求，不展开实现方案，不讨论代码拆分、线程模型、调度细节和具体接口。

本次目标只有四个：

1. 明确秘书只在特定阶段参与，不得长期夹在助理主链路中
2. 明确秘书必须走委托机制，便于本地观察其判断记录
3. 明确秘书不允许调用工具，其职责仅限“是否需要回”的判断
4. 明确助理进入在场后，后续消息不再经过秘书重复把关

## 二、前提共识

本计划基于以下业务前提：

1. 远程联系人发来的消息，无论助理当前是否在场，都会先进入会话历史
2. 这些消息会成为后续上下文候选，不能因为秘书是否参与而跳过持久化
3. “秘书是否参与”解决的是回复决策问题，不是收信、存档或上下文接入问题

换句话说：

远程 IM 的消息入口始终存在，秘书不是消息入口守门人，而是“离场阶段是否需要转入作答”的判断者。

## 三、角色边界

### 3.1 秘书

秘书的职责只保留为一件事：

- 判断当前这条或这一批新消息，是否值得让助理正式介入回复

秘书不负责：

- 直接回复远程联系人
- 调用任何工具
- 长时间接管后续消息流
- 代替助理维持持续对话

### 3.2 助理

助理负责：

- 真正生成回复
- 进入在场模式后的连续处理
- 对后续排队消息进行正式作答

助理一旦进入在场模式，本轮机制的主导者就是助理，不再是秘书。

## 四、核心机制需求

## 4.1 离场阶段

当助理处于离场状态时，收到新的远程 IM 消息后：

1. 消息先正常入历史
2. 进入“是否需要回”的判断阶段
3. 该判断必须由秘书承担
4. 秘书的这次判断必须以委托形式出现，能够被本地用户观察到

秘书判断结果只允许两类：

1. 不需要回
2. 需要回

若秘书判定“不需要回”：

- 本轮结束
- 助理保持离场

若秘书判定“需要回”：

- 助理切换为在场
- 由助理接手正式回复

## 4.2 在场阶段

当助理已经处于在场状态时，后续新消息到来应直接进入助理队列。

这个阶段的要求是：

1. 新消息仍正常入历史
2. 新消息直接排队给助理
3. 秘书不再参与“是否需要回”的二次判断
4. 不允许出现“每来一条新消息都再先过一次秘书”的机制

也就是说：

秘书只负责把助理从离场推入在场，不负责在场后的持续把关。

## 4.3 在场后的排队语义

助理进入在场后，如果此时又来了新消息：

1. 不重新跑秘书
2. 不重新做“是否值得回”的入口判定
3. 直接按助理当前的忙闲状态进入排队或续跑

这里的重点不是并发实现，而是业务语义：

在场之后，消息流是“无脑排队给助理”，不是“继续由秘书筛一遍”。

## 五、委托可见性要求

秘书必须走委托机制，原因不是为了让它执行工具，而是为了让用户在本地看到它做过判断。

本次可见性的要求如下：

1. 本地用户应能看到秘书参与过一次判断
2. 本地用户应能看到秘书的判断结论
3. 这份记录应表现为委托记录，而不是工具记录
4. 远程联系人侧不应看到秘书内部判断过程

这里需要特别区分两件事：

1. 行动记录
   - 本次不要求，因为秘书本来就不允许调用工具
2. 判断记录
   - 本次必须保留，因为这是用户需要观察的对象

## 六、秘书能力限制

秘书的能力边界需要钉死：

1. 秘书不允许调用工具
2. 秘书不允许发出远程消息
3. 秘书不允许替代助理进入持续作答状态
4. 秘书只做轻量判断，不承担执行责任

因此，秘书的“委托化”不是给它更多权限，而是把它的判断过程纳入统一可观察链路。

## 七、状态切换要求

本次机制重构后，至少应满足以下状态语义：

1. 初始可处于离场
2. 离场时由秘书决定是否转入在场
3. 一旦因“需要回”转入在场，后续消息默认继续由助理承接
4. 在场期间秘书退出主链路
5. 何时再次离场，属于后续在场状态机范围，但离场前不应重新引入秘书

这里要避免的不是某个实现细节，而是语义倒挂：

不能出现“已经在场了，但每次来新消息还是先问秘书要不要让助理回”的情况。

## 八、用户可感知结果

从用户视角，本次改造后的体验应当是：

1. 助理不在场时，秘书像门卫一样做一次是否值得介入的判断
2. 一旦秘书放行并触发助理出场，后面就是助理持续接球
3. 本地能看到秘书这次判断发生过
4. 远程对端只看到最终是否回复，不看到秘书内部过程

## 九、非目标

本计划暂时不覆盖以下内容：

1. 秘书具体提示词怎么写
2. 委托线程、调度器、运行时状态如何落代码
3. 在场多久后离场
4. 多联系人之间的优先级与抢占
5. 秘书判断结论的数据结构细节
6. 调试日志、埋点字段和界面展示样式

这些都属于后续实现设计，不在本次需求冻结范围内。

## 十、验收口径

只有同时满足以下判断，才算本次机制需求成立：

1. 离场时，秘书会以委托形式参与“是否需要回”的判断
2. 秘书不具备工具能力
3. 本地能观察到秘书的判断记录
4. 秘书判定需要回后，助理进入在场并实际接手回复
5. 助理在场后，新消息直接排队给助理，不再重复经过秘书
