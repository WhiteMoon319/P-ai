# 远程应答委托统一调度与投递计划

## 原始要求（不可偏离）

1. 远程应答本质上是委托，必须有独立 `delegate_id`、独立委托会话、状态、历史、详情和可中止能力。
2. 会话控制面板与侧边栏复用同一委托状态数据源，同时显示普通与远程应答委托；完成、失败和中止后仍保留历史。
3. 点击远程应答委托与普通委托一致，展示独立委托会话中的答复详情。
4. 保留现有远程语义：首发冻结提示词快照；秘书引导只影响后续轮次；画像唯一目标为触发消息发送者，最多 12 条。
5. 远程应答不进入 `enqueue_session_notification_dispatch`，不使用普通委托完成投送；联系人会话直写与远程外发保持现状。普通委托投送优化属于独立计划。
6. 远程运行不把联系人主会话标为普通 `AssistantStreaming`；秘书判断活跃远程应答委托，不依赖主会话忙碌态。
7. 现有工具前后中间正文仍按原语义直写并外发，不能因接入委托看板而丢失或重复。

## 设计结论：持久化外壳接入

不把远程应答迁入标准 `delegate_run_thread_to_completion`，不替换它现有的执行、并发、上下文冻结、联系人直写或外发链路。

只扩展现有远程应答委托：启动时创建普通委托已经使用的 `DelegateEntry` 和独立 delegate conversation；远程运行态继续作为执行真相，新增的持久化记录和会话作为看板、历史、详情、取消入口与重启后的诊断载体。

普通委托会话实际存放在应用数据根的 `delegate-conversations/`，并非远程联系人目录；通过 `root_conversation_id=联系人会话 ID` 挂载。这一既有关系足以让两处 UI 直接发现远程委托，无需给远程会话改目录或改主消息存储。

```text
现有远程应答执行（保留）
  remote_im_reply_delegate_runtimes
    -> 冻结快照 / 秘书引导 / semaphore
    -> send_chat_message_inner(联系人主会话)
    -> 联系人会话直写 + 远程外发（保持原样）

新增持久化外壳（最小扩展）
  DelegateEntry(kind=remote_im_reply, conversation_id=联系人主会话)
    -> delegate-conversations/<delegate_id>/（详情镜像）
    -> 委托状态事件 / 控制面板 / 侧边栏 / 历史 / 取消入口
```

## 最小改动切面

### 1. 创建持久化委托外壳

- 创建 `DelegateEntry(kind=remote_im_reply)`；`conversation_id` 继续沿用当前字段含义，即联系人主会话/root conversation。ID 只允许由一个入口生成：使用 `delegate_store_create_delegate(...)` 返回的 `delegate_id` 作为 remote runtime、chat key、委托会话和状态事件的唯一 ID，不能保留 remote UUID 再生成第二个 store ID。
- 复用 `delegate_runtime_thread_build` / 委托会话存储创建 `id=delegate_id` 的独立会话，`root_conversation_id` 指向联系人主会话。不得修改现有 `DelegateEntry.conversation_id` 的语义，也不引入第二套 root/execute ID 数据库迁移。
- 创建时明确从远程 `session_info` 取得 source/target department、agent 与目标 API，并生成非空 title/goal；这是现有 `DelegateCreateInput` 和 `delegate_runtime_thread_create` 的强制前置条件。
- 独立会话写入最小可诊断首发记录：冻结快照和触发消息 ID 以 `provider_meta.remote_im_delegate_internal=true` 标识为内部上下文。扩展委托详情读取路径过滤该标记；不能假定现有前端投影会自动隐藏内部消息。
- 若持久化外壳创建失败，远程应答不启动，返回可读错误；避免出现已外发却没有可追溯委托的半成品。无需把两个现有存储伪装成事务。

### 2. 保留原执行，镜像详情与状态

- 继续使用 `remote_im_reply_delegate_runtimes` 保存首发快照、待消费引导、联系人、并发 permit 和实际活跃判定；不把它迁入标准调度器。
- runtime 新增 `cancelled` / `terminal` 标志；取消、模型失败、引导读取失败、semaphore 获取失败和正常清空都必须通过同一个“取得终结权”入口。只有取得终结权的路径可归档 shell、更新 `DelegateEntry` 和发送状态事件。
- 排队任务在 acquire semaphore 后必须再次检查 `cancelled` / `terminal`，已取消则直接退出；运行中的一轮在写联系人会话、外发前同样检查终结状态，避免取消后仍发送。
- 每次引导入队时，同时向独立委托会话追加带内部标记的引导记录，供排障与重启后识别，但不改变本轮/下轮的现有消费顺序。
- 在现有远程可见文本已被识别的位置，将同一不可变文本镜像到 delegate conversation。联系人会话直写、自动外发、阶段顺序、消息 ID 和幂等逻辑均不移动、不重写；镜像只服务详情，绝不能再触发外发。
- 每轮成功、失败、取消和最终结束时更新 `DelegateEntry` 状态、归档 runtime thread、发送既有委托状态事件。远程完成路径只做状态收尾，硬禁止调用 `delegate_enqueue_result_message(...)` 与 `enqueue_session_notification_dispatch(...)`。

### 3. 统一面板和取消

- 远程启动后将其 delegate runtime thread 置入现有活跃线程集合，使 `list_conversation_delegate_statuses` 无须新数据源即可显示活跃项；结束后复用近期/持久委托会话历史。
- 摘要增加 `kind` 供 UI 仅作标签或图标区分；控制面板和侧边栏继续消费同一个 `ConversationDelegateStatusSummary`。
- 详情继续调用 `get_delegate_conversation_block_page`，只按块分页读取独立委托会话。
- 取消入口按 `DelegateEntry.kind` 分支：普通委托保留 `abort_delegate_runtime_thread`；远程新增专用取消函数，按 `remote-im-reply-delegate::<delegate_id>` 取消聊天句柄，并按远程 session key 取消工具句柄、标记 runtime 已取消。不能假定普通委托的 `department::delegateId` chat key 能取消远程专用任务。
- 启动恢复扫描未终结远程 `DelegateEntry`；不重跑模型，统一更新为明确失败/中断状态并保留独立会话。不能让重启后的持久记录继续显示创建时的 `delivered`。

## 明确不做

- 不把远程执行改为在 delegate conversation 上调用 `send_chat_message_inner`。
- 不拆或重写 `core_send_inner.rs` 的远程联系人直写、自动外发、中间阶段处理或冻结上下文逻辑。
- 不新建远程输出 outbox、平台投递状态机、`unknown` 恢复策略或跨存储 saga；这是投送可靠性优化，若需要应另立计划。
- 不改普通委托完成投送，不触碰 `20260710_普通委托完成消息投送机制优化计划.md` 的边界。
- 不自动恢复或重跑进程重启前的远程模型执行；重启后保留持久详情和最后状态即可。

## 验证矩阵

- 触发远程应答后，`DelegateEntry`、独立委托会话、控制面板和侧边栏同时出现；运行中、完成、失败、中止后均可打开详情。
- 联系人主会话的消息、远程外发次数、工具前后中间文本、首发冻结和秘书引导时序与改造前一致。
- 委托详情包含已产生的可见答复和必要内部诊断记录，但不把冻结快照/秘书引导渲染为普通聊天正文。
- 首发画像仍只属于触发消息 sender，最多 12 条；运行中不设置联系人主会话普通忙碌态。
- 取消能停止远程专用执行并保留历史；远程完成、失败、取消均不进入普通结果回注或系统通知队列。
- 模拟 semaphore 等待中取消、运行中取消、模型失败与正常完成并发，确认只有一个终态写入，取消后不再写联系人会话或外发。
- 模拟重启，确认未终态远程委托显示为失败/中断，而非错误保留 `delivered`；不触发模型重跑。
- 普通委托创建、完成、取消和既有投送回归不变。

## 风险边界

- 外壳持久化必须先于远程模型启动；否则仍会产生不可见、不可取消的远程任务。
- 镜像是单向的：联系人会话仍是对外投递真相，delegate conversation 仅用于委托详情；不得从镜像反向触发发送。
- 远程取消需要使用其现有专用 chat key，不能生搬普通委托取消逻辑。
- 远程运行态移除与终态更新必须具备唯一终结者；否则取消和完成竞争会产生假完成、重复归档或取消后外发。
- 内部快照/引导没有既有隐藏语义，必须在委托详情数据入口过滤 `remote_im_delegate_internal`，不能只靠前端约定。
- 不读取完整联系人会话来补详情或上下文；快照来自现有运行态，详情从 delegate conversation 分页读取。
- 本计划确认前不进入实现阶段。
