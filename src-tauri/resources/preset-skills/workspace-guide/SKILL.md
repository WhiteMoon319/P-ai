# 当前工作区与项目资产指南

## 适用范围

本 Skill 只处理**当前会话工作区及其项目**。助理空间的共享 Skill、MCP、人格与跨项目资源，使用 `assistant-space-guide`。

开始工作时先确认当前工作目录、Git 仓库根目录和未提交改动。已有改动是当前事实，未经确认不得按旧版本推断或覆盖。

不要因为开始新任务就克隆仓库、创建 `projects/`、`scratch/` 或替代目录。用户提供的当前工作区就是默认执行边界；需要隔离开发时，只有用户要求或项目机制明确要求才创建 Git worktree。

## AGENTS.md

`AGENTS.md` 是项目级协作约束，不属于 `.pai/`。

- 动手前读取当前工作区适用的 `AGENTS.md`；若子目录有更近的 `AGENTS.md`，同时遵守其局部约束。
- 以其中的构建、测试、提交、文件组织和风险规则为准。
- `.pai/skills/` 可以补充项目专用工作方法，但不能覆盖 `AGENTS.md`、用户当前指令或更高层约束。
## 项目级 Skill 与工作流

项目级 Skill 默认位于项目 `.pai/skills/`，也可能位于项目根目录的 `skill/`；项目工作流位于 `.pai/workflow/`。它们都属于当前项目范围，不属于助理空间。

应主动维护项目级 Skill 与工作流：

- 当前任务需要稳定复用的项目规则、步骤或检查清单，而现有内容缺失时，创建项目级 Skill 或工作流；
- 现有项目级 Skill 或工作流已经过期、错误、与项目现状或 `AGENTS.md` 冲突时，先调查影响，再修正；
- 内容重复时，收敛为单一清晰规则，避免多个项目文件给出互相矛盾的指引；
- 变更只覆盖项目范围，不把项目规则写入助理空间；不以项目级 Skill 或工作流替代 `AGENTS.md`、用户当前指令或更高层约束。

涉及删除、迁移或大范围重写时，先说明范围和影响并取得用户确认。

## .pai/：项目级 PAI 资产

项目根的 `.pai/` 保存与**这个项目**相关的 PAI 工作资产。它通常被 Git 忽略；是否提交某个文件必须由项目规则和用户明确决定，不能因为文件位于 `.pai/` 就默认提交。

常用目录职责：

| 目录 | 用途 |
| --- | --- |
| `.pai/skills/` | 项目专用 Skill。仅对当前项目生效。 |
| `.pai/mcp/` | 项目级 MCP 的预留位置。当前 PAI 尚不支持项目级 MCP 配置、自动加载或连接管理；不要把它当作已生效的配置入口。 |
| `.pai/plan/{domain}/` | 当前项目按业务领域归类的计划文件。存在会话工作目录时，计划优先写入对应领域目录。 |
| `.pai/report/` | 需要保留的审查、调查、验收或分析报告。 |
| `.pai/workflow/` | 项目固定工作流和操作说明。 |
| `.pai/reference-projects/` | 为当前项目保留的外部参考仓库；它们有自己的 Git 状态，不能当作本项目源码修改或提交。 |
| `.pai/.worktree/` | 项目隔离开发工作树。每个工作树都是独立的真实修改面，先检查状态再操作。 |
| `.pai/temp/` | 可丢弃的任务过程产物。 |

目录不存在时，不为形式而创建；仅在当前任务确实需要相应资产时创建。

## 计划、报告与正式文档

- 用户明确要求计划、重构或新功能域设计时，先按主要业务产出选择领域，再在 `.pai/plan/{domain}/` 编写计划并等待确认后实现。
- 不按 `active`、`archive` 或年月创建额外层级；计划完成后保留在原领域目录。
- 计划提交后路径保持稳定；后续确认、继续执行和完成标记不得擅自移动该计划。
- 需要长期保留、可供后续协作引用的调查或审查结论，放入 `.pai/report/`。
- 面向产品用户、开发者或发布流程的正式文档，按项目现有 `docs/`、README 或用户指定位置存放；不要因为是 Markdown 就一律放到 `.pai/`。
- 计划和报告是项目过程资产；是否归档、移动或纳入提交，以用户和项目规则为准。

## 临时产物

统一使用 `.pai/temp/`。

以下过程材料默认放入 `.pai/temp/`，避免堆在项目根目录并被误交付或误提交：

- 调试输出、命令记录、一次性分析草稿；
- 截图、录屏、预览图、导出物和对比文件；
- 临时脚本、验证数据、原型页面、可再生成的构建产物。

`.pai/temp/` 的内容默认可清理，不是长期事实来源，也不应直接提交。需要正式交付或长期引用时，再按用户指定位置转为正式产物；删除既有文件前仍须先确认删除范围和影响。

## 进入项目后的最小动作

1. 确认工作目录、仓库根目录、当前分支和未提交改动。
2. 读取适用的 `AGENTS.md`，再按任务读取必要的 README、包清单、构建配置或目标代码。
3. 使用项目原生工具链和最小相关验证；不要自行替换包管理器、格式化器或构建方式。
4. 修改范围只覆盖用户要求。遇到工作树、临时产物或参考仓库时，先分清它们是否属于当前目标。
5. 汇报实际改动、验证结果和遗留的临时产物；不要把未验证的推测写成结论。
