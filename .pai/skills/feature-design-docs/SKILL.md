# PAI 功能设计文档写作 Skill

## 为什么写设计文档

设计文档不是代码说明书，不回答"代码怎么实现"，而回答：

- 这个功能做什么，不做什么
- 为什么这么设计，为什么不走另一个方案
- 依赖什么外部条件才能成立
- 产出什么，谁消费
- 怎么算完成，哪些情况算降级

## 文档结构

下面是一个推荐骨架，但不必严格套用。你可以按功能特点调整章节顺序，删掉不适用的，合并相近的。

```md
# 标题

## 目标

写这个功能做什么、不做什么。

推荐拆成两段：

当前实现：
- ...

未实现：
- ...

## 需求收口

具体的需求描述。最好能让人闭眼就能想象用户操作或系统行为。

## 实现原则

重要的设计取舍。为什么要这样做，为什么不那样做。

每一条原则应该是一个可追溯的决策，而不是空话。

## 方案

具体的做法。可以分点、分模块、分前后端写。

重点是：做了什么、产出什么、谁负责。

## 交互 / 流程（可选）

如果涉及用户操作，写清楚用户做了什么之后系统发生什么。

如果只是后端内部机制，可以不写交互。

## 边界与降级

明确不做什么，以及失败时怎么处理。

## 未实现（可选）

当前明确不做的事。写成陈述句，不要写成"后续可扩展"。

例子：

```
- MCP 服务热插拔事件通知：当前变化只由主动 reload 或操作命令触发，不广播。
- 服务健康状态持续监听：当前只在启用时探测一次，不会自动重试或保活。
```
```

## 写作要点

### 1. 写方案，不写代码

方案和代码的区别：

| 方案 | 代码 |
|------|------|
| 建议前端渲染后截图 | 用 `html2canvas` 的 `toBlob` 方法导出 |
| stdio 子进程通过 Windows Job Object 托管进程树 | 在 `mcp_connect_stdio_command` 中调用 `mcp_try_attach_windows_process_tree_guard` |

方案说"做了什么"，代码说"哪个函数怎么调用"。设计文档只需要前者。

### 2. 写决策，不写描述

"采用前端渲染后截图，因为消息布局在前端、样式一致性更好"——这是决策，有人能看懂为什么选这个。

"首先生成图片，然后保存到本地"——这是描述，看完也不知道为什么这么做。

### 3. 写边界，不写潜力

"暂不包含直接分享到微信"——这是边界，接手者知道不该做什么。

"后续可扩展到微信分享"——这是潜力，接手者不知道这轮做不做。

### 4. 写约束，不写流程

"HTML 分享不依赖应用运行时可打开"——这是约束，决定了实现上必须内联样式、不能依赖路由。

"打开 HTML 文件后应用会初始化页面"——这是流程，没说到点子上。

## 写之前先确认

### 1. 确认功能的核心价值

写文档前先问自己：这个功能为什么存在？它的核心产出是什么？

例子：

| 功能 | 表面做的事 | 核心价值 |
|------|-----------|---------|
| 归档 | 把会话移出活跃列表 | 归档后用 LLM 反思对话，提炼记忆和画像更新 |
| MCP | 连外部服务、发现工具 | 管理外部进程生命周期，防止卡死拖死主程序 |

只写表面操作会让文档像操作手册，不写核心价值接手者看不懂为什么要做这个功能。

### 2. 确认功能边界是否独立

两个功能如果在代码层面有重叠（共用模块、共用 pipeline），但设计目标不同、触发条件不同、产出不同，就必须拆成两篇独立的文档。

**判定标准：如果两功能不共享「功能目标」和「触发时机」，就应该分开写。**

例子：

- 归档和上下文整理都用到了 archive_pipeline，但归档的目标是把会话转历史资料、核心产出是记忆提炼；上下文整理的目标是压缩上下文窗口、核心产出是摘要消息。两篇分开写。
- 用量统计和成本观测都用到了 usage 数据，但统计归会话入账、观测归概览聚合。如果目标不同就分开写。

### 3. 确认用户说的功能名对应什么

用户说的功能名可能和代码中的命名不完全一致，也可能和你的第一直觉不同。动笔前先确认：

- 用户说的这个功能名，在系统里对应什么行为？
- 它不包含什么？哪些看起来相关但其实是另一个功能？

如果不确定，先问清楚再写，不要猜。

## 写什么类型的文档

不同类型的文档关注点不同，但共同点是：**不写函数调用链，不写代码路径，不写数据字段全表。**

### 功能扩展（如分享图片、分享 HTML）

重点写：做什么、不做什么、方案选型、前后端分工、验收标准。

参考本仓库 `.pai/plan/ui/20260421_消息多选分享图片与HTML计划.md`。

### 后端机制（如 MCP 管理、归档、上下文整理）

重点写：功能目标、核心价值、触发条件、方案、边界与降级。

参考本仓库 `docs/features/mcp/20260709_MCP管理服务后端设计.md`。

### 系统边界（如前后端分工、模块职责）

重点写：职责分界、调用方向、共享状态、不做什么。

## 禁止内容

以下内容不要写进设计文档：

- 函数调用链。不要用 `→` 串函数名。
- 代码文件路径和行号。接手者不需要知道文件在哪。
- 结构体字段全表。接手者不需要知道每个字段的类型和默认值。
- `证据来源` 整节。
- `待确认问题` 整节。
- 抽象目标。如"提升可观测性""保证稳定可靠"。
- 实现细节。如"调用某函数的第几个参数"。

## 自检

写完后检查：

- 读者看完能否说清这个功能做什么、不做什么？
- 这个功能最核心的价值/产出是否写清楚了？（不只是表面操作）
- 如果文档提到方案，有没有写为什么选这个方案？
- 有没有函数调用链、代码路径、字段清单？
- 有没有抽象目标和空话？

如果以上都通过，文档就是合格的。
