# 20260713_远程应答委托系统提醒上下文注入计划

## 用户原始关键指令

> "在meta 前面，增加一块系统提醒，里面包括当前用户画像， 其他正在处理的应答委托，比如说，正在处理"另外一个人的另外一句话""
>
> "这样助理就可以知道，自己已经回答过另外一句话"
>
> "补充，这个注入应该在本次委托内作为稳定的上下文"
>
> "一个委托的上文，不是在委托中稳定的吗？就是抓一次快照，然后上文就不变了，后续不要再改了"

## 一、目标

在远程应答委托构造既有初始上文快照时，为最后一句用户消息补入 `[系统提醒]`，让助理感知当前联系人画像以及其他正在处理的委托，避免重复应答。委托上文本来就是一次构造、后续稳定复用，不新增第二套“冻结”机制。

## 二、需求描述

### 2.1 注入内容

远程应答委托创建、裁剪初始历史上文时，生成一条 `[系统提醒]` 块，包含：

1. **当前联系人的用户画像** — 由 trigger message 的 sender user_id 查询 memory store 获取该联系人的画像记忆
2. **其他正在处理的应答委托列表** — 从 `remote_im_reply_delegate_runtimes` 快照中，排除当前委托自身，列出其余活跃委托的联系人称呼和触发消息摘要
3. **当前会话应答账本** — 直接从已经取得的初始上文快照中整理触发消息之前已完成的“用户消息 → 助理回答”，不额外读取整份会话

### 2.2 接入既有初始上文快照

系统提醒直接写入 `prompt_snapshot_messages` 中触发消息的 `extra_text_blocks` 首位。提示词组装时，该块自然位于最后一句用户发言的 meta 之前；meta 和原消息正文随后排列。活跃委托只列出当前会话内的其他运行中应答委托，应答账本只使用本次已经取得的初始上文。后续轮次继续使用同一份 `prompt_snapshot_messages`，不增加独立提醒字段、不通过 `RuntimeContext` 每轮重复注入，也不重新扫描画像或委托运行态。

### 2.3 移除旧冗余块

原先通过 `build_remote_im_transient_profile_blocks` 附加在 `extra_blocks` 末尾的 `<user profile snapshot>` 块不再需要，其内容已合并到 `[系统提醒]` 的"当前联系人画像"中。

### 2.4 生成结果验证

测试最终生成的请求消息，而不只检查中间字段：最后一个 user message 的文本块顺序必须严格为 `[系统提醒]`、`meta_text`、`trigger_message_text`；对同一初始上文重复组装，结果必须完全一致，且不得再出现独立 `<user profile snapshot>` 块。

## 三、最终请求体格式

```json
{
  "system": "...",
  "messages": [
    "...(历史冻结消息)...",
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "[系统提醒]\n当前联系人画像：\n{联系人画像}\n\n当前会话正在处理的应答委托：\n- {联系人A}：\"{触发消息摘要}\"\n\n当前会话应答账本：\n- 已应答：\"{用户消息}\" → \"{助理回答}\""},
        {"type": "text", "text": "{meta_text}"},
        {"type": "text", "text": "{trigger_message_text}"}
      ]
    }
  ]
}
```

### 格式说明

- `[系统提醒]` 块位于 `content` 数组**最前面**
- `meta_text` 位置不变（紧跟在 `[系统提醒]` 之后）
- `trigger_message_text` 位置不变（紧跟在 `meta_text` 之后）
- 不再有单独的 `<user profile snapshot>` 块
